# Sub-Skill: OpenSpec Tests

> 由 `implement-issue-with-test` 主 skill 在步驟 5 載入。完成後回到主 skill，繼續載入 `openspec-apply.md`。
>
> **在寫任何一行實作程式碼之前，先把測試寫出來。**

## 目的

依 `openspec-propose` 階段確認的 Given-When-Then 場景，在專案實際使用的測試層級（單元測試／整合測試／E2E 測試，依專案而定）產生對應的測試程式碼，並讓使用者 Review 測試涵蓋範圍是否正確。本步驟**只寫測試，不寫任何產品程式碼**（除非專案既有工具函式已存在，允許在測試中直接引用）。

不同專案的測試層級不一樣：有些專案只有單元測試，有些單元測試與 E2E／整合測試都有。本步驟不預設每個專案都要有 E2E，也不強迫每個場景都要寫成端到端測試，而是依專案現況決定合適的層級。

TDD 精神：測試要能表達「預期行為」，而不是等實作寫完後才回頭套用斷言。此階段完成後，測試應該是可執行、會失敗的（red），失敗原因是「功能尚未實作」，而不是測試本身寫錯。

---

## 1. 確認測試框架、慣例與測試層級

參考 `openspec-explore` 步驟 6.1 已確認的測試慣例與測試層級。若尚未確認，先執行：

```bash
# 依專案技術棧尋找既有測試設定，例如：
cat package.json | grep -A5 '"scripts"'
# 找出專案實際有哪些測試層級，例如：
# - 單元測試：jest / vitest / pytest 等，測試檔多半緊鄰原始碼或在 __tests__ / tests 資料夾
# - 整合測試：測試多個模組協作、或搭配測試資料庫
# - E2E 測試：cypress / playwright 等，通常有獨立的 e2e/ 資料夾與設定檔
```

向使用者確認偵測結果，例如：「這個專案偵測到單元測試（Jest）與 E2E（Playwright），這次兩個層級都要寫，還是只寫單元測試？」

若專案中完全找不到既有測試框架可依循（例如全新專案、尚未安裝任何測試工具），停止並詢問使用者要採用哪個測試框架，不可自行安裝或決定。若專案已有某個層級（例如只有單元測試），**不要**自行額外引入專案本來沒有的測試層級（例如擅自加裝 E2E 框架），除非使用者主動要求。

---

## 2. 決定每個場景要在哪個層級寫測試

對 Spec 中 `specs/` 裡的每一個 Given-When-Then 場景，依專案實際擁有的測試層級決定測試怎麼寫：

- **專案只有單元測試**：把場景拆解成一個或多個單元測試，鎖定這次改動涉及的函式／模組／元件本身的輸入輸出與行為即可，不用勉強在單元測試裡模擬完整的端到端流程。
- **專案同時有單元測試與整合／E2E 測試**：依場景性質選擇合適層級，兩者可以搭配使用：
  - 涉及跨模組、真實使用者操作路徑、或需要串接後端／資料庫驗證整體行為的關鍵場景 → 適合寫一個整合／E2E 測試
  - 場景背後的細節分支、邊界值、錯誤處理邏輯 → 用單元測試覆蓋，不必每個分支都重新跑一次 E2E（成本高、執行慢，也不易維護）
  - 一個 Spec 場景可以對應多個測試（例如一個 E2E 測試涵蓋主要路徑，搭配數個單元測試涵蓋該路徑上的分支），不強制「一場景一測試」，只要合起來完整驗證該場景的 Given-When-Then 即可
- 不論哪種情況，每個 Spec 場景（含邊界情況）最終都必須有至少一個測試涵蓋到，不可有場景完全沒有任何層級的測試對應
- 「不在範圍」的項目**不需要**寫測試
- 若某個場景實際寫測試時發現難以斷言、邏輯有矛盾，或無法判斷該用哪個層級驗證，停止並回報使用者，可能代表 Spec 場景本身需要修正，不可自行簡化場景意圖來遷就好寫的測試

## 3. 撰寫測試

不論在哪個層級，測試內容都對應 Given-When-Then 的結構：

- **Given** → 測試中的前置設定（setup / fixtures / mock，或 E2E 中的初始頁面狀態／登入狀態）
- **When** → 測試中實際觸發的行為（呼叫函式、送出 request、觸發互動、E2E 中的使用者操作）
- **Then** → 測試中的斷言（assertion，或 E2E 中對畫面結果的驗證）

命名應能反映測試驗證的行為，並在測試檔案或該群組測試的描述（`describe`）中標註對應到哪個 Spec 場景，例如場景「使用者輸入空白訂單編號時顯示錯誤訊息」對應單元測試 `it("shows an error message when order number is blank", ...)`。

單一場景拆解出的邊界值、分支測試，**不需要**每一條都逐字比對場景敘述硬湊命名；只要該群組測試合起來能證明場景的 Given-When-Then 成立即可（呼應第 2 節「一個場景可對應多個測試」的彈性）。

---

## 3.x GWT 場景之外，補齊 coverage

Spec 中的 Given-When-Then 場景描述的是**業務層面的預期行為**，是測試設計的起點，但不等於程式碼覆蓋率的終點。只靠 Spec 場景反推測試，coverage 通常會有漏洞（例如 Spec 沒寫到的 null 值、例外分支、防禦性程式碼）。撰寫測試時，除了確保每個 Spec 場景都有對應測試，也要視實作的程式碼路徑，補上 Spec 未明講、但邏輯上存在的情境，例如：

- **邊界值**：空字串、`null`／`undefined`、0、負數、超長輸入、極大值
- **例外與錯誤路徑**：函式內的 `throw`、`catch`、防禦性判斷（例如參數型別不符）
- **分支覆蓋**：`if/else`、`switch`、三元運算子等每個分支至少走過一次
- **既有邏輯的迴歸保護**：這次改動經過、但 Spec 沒特別描述的既有函式邏輯，避免改壞

這些補充測試**不必**勉強套上一句對應的 Spec 場景敘述或編號，可以直接依函式簽章／輸入輸出設計，但仍建議放在同一個 `describe` 底下，並用測試名稱清楚說明驗證的是哪個邊界或分支，方便日後回頭追蹤這條測試存在的理由。

## 4. 執行測試，確認處於 red 狀態

依步驟 1 確認的測試層級，分別執行對應指令：

```bash
# 例如分別執行專案既有的單元測試與 E2E 測試指令（參考 package.json scripts）
```

確認：
- 新增的測試都能被執行（不是被跳過或語法錯誤而沒跑到）
- 新增的測試目前**全部因為功能未實作而失敗**（red），而不是因為測試本身寫錯而失敗或誤判通過
- 若有測試在功能未實作的情況下就通過了，代表該測試沒有真正驗證到行為，需要修正測試

---

## 5. 人類 Review：確認測試涵蓋範圍

向使用者展示測試清單、對應的 Spec 場景與所在的測試層級，例如：

```
## 測試涵蓋範圍

| Spec 場景 | 測試層級 | 測試案例 | 目前狀態 |
|-----------|----------|----------|----------|
| 正常送出訂單 | E2E | submits an order from the form | ❌ red（預期，功能未實作） |
| 訂單編號為空 | 單元測試 | it("shows an error when order number is blank") | ❌ red（預期，功能未實作） |
| ... | ... | ... | ... |
```

**等待使用者確認**：
- 涵蓋範圍是否正確、是否有遺漏場景
- 測試層級的選擇是否合理（例如是否有場景被過度寫成 E2E、或該有整合驗證的地方只寫了單元測試）
- 測試的斷言方式是否符合預期（例如是否測到真正該測的行為，而非只測到表層）
- 搭配 coverage report 檢查本次改動涉及的程式碼路徑（尤其是新增的分支與例外處理）是否有明顯遺漏

若使用者提出調整，修改測試後重新執行確認仍為 red 狀態，再次請使用者確認，不得跳過確認直接進入實作。

---

## 完成條件
- Spec 中的每個 Given-When-Then 場景都已在合適的測試層級有對應的測試案例
- 除 Spec 場景外，本次改動涉及的程式碼分支與邊界情況已有對應測試覆蓋，coverage report 未出現明顯遺漏的未測試路徑
- 測試可執行，且目前皆為 red（因功能未實作而失敗，非測試本身錯誤）
- 使用者已 Review 並確認測試涵蓋範圍與層級選擇皆正確

接著載入 `sub-skills/openspec-apply.md`，以 TDD 方式實作：先確認測試失敗，再寫最少必要的程式碼使其通過。
