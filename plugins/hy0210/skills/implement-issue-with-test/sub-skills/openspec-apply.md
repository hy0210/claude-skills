# Sub-Skill: OpenSpec Apply

> 由 `implement-issue-with-test` 主 skill 在步驟 6 載入。這是最後一個步驟，完成後整個 `implement-issue-with-test` 流程結束。
>
> 進入本步驟時，`openspec-tests` 產出的測試應該都已存在且處於 red 狀態（因功能未實作而失敗）。本步驟只寫**讓測試通過所需的最少實作程式碼**，不重新設計測試。

## 關於 /opsx:apply

`/opsx:apply` 是 OpenSpec 的斜線指令，在 Claude Code 的聊天框中輸入。它讀取 `openspec/changes/<change-name>/tasks.md`，逐項實作並打勾，直到所有任務完成。

⚠️ 不要用 bash 執行 `openspec apply`。`/opsx:apply` 是在 Claude Code 聊天中輸入的斜線指令。

---

## Figma MCP 規則（必讀，本 sub-skill 全程適用）

若實作涉及 UI 或樣式，先載入 `figma-link-guard` skill 並依其規則處理連結開啟與例外狀況。

本步驟是**精確樣式驗證**（顏色、字型、間距、尺寸等），遇到 `figma-link-guard` 規則 2（資料過大）時，走「需要嚴格樣式」路徑（不可改用截圖，停下詢問使用者）。驗證本身必須比對 Figma **節點樣式數值**，不可用截圖替代。

---

## 1. 啟動 /opsx:apply（TDD 迴圈）

在 Claude Code 聊天中輸入 `/opsx:apply`，OpenSpec 將逐步執行 `tasks.md` 中的任務。**每個任務都依照以下紅燈→綠燈迴圈進行**，不可整批任務寫完程式碼才一次執行測試：

1. **確認 red**：先找出這個任務對應的測試案例（`openspec-tests` 已產出），執行它，確認目前失敗，且失敗原因與「功能尚未實作」相符
2. **寫最少必要的實作程式碼**：只寫剛好能讓這個測試通過的程式碼，不預先實作尚未被任何測試涵蓋的行為
3. **確認 green**：重新執行測試，確認通過；同時執行整體測試套件，確認沒有讓其他既有測試變成失敗
4. **視需要重構**：在測試維持通過（green）的前提下，可以調整程式碼結構、命名、重複邏輯，但不可改變行為
5. 進到下一個任務，重複上述迴圈

實作過程遵守：
- 只實作 `tasks.md` 範圍內的任務，不做額外重構
- 遵循 `/opsx:explore` 階段確認的程式碼風格與架構
- 遇到 tasks 範圍外的問題（技術債、潛在 bug），記錄但不主動修改

---

## 2. 絕對不可為了讓測試通過而修改測試

實作過程中如果卡在某個測試一直無法通過，**先假設是實作有問題**，而不是去放寬斷言、註解掉斷言、或跳過（skip）該測試。

若排查後認為問題出在測試本身（例如測試案例與 Spec 場景理解不一致、斷言方式有誤），**停止並詢問使用者**，說明你認為測試哪裡有問題、建議如何調整，取得使用者同意後才可修改測試，不可自行決定修改測試內容。

若發現某個 Spec 場景在實作時才發現無法如期達成（例如與既有架構衝突），同樣停止並詢問使用者，不可自行簡化行為讓測試「勉強」通過。

---

## 3. UI 任務完成後：Figma 樣式比對

每個涉及 UI 的任務完成測試（green）後，立即用 Figma MCP 驗證：

1. 開啟對應的 Figma 節點
2. 逐一比對：
   - 顏色（fill、stroke、text color）
   - 字型（family、size、weight、line-height、letter-spacing）
   - 間距（padding、margin、gap）
   - 尺寸（width、height、border-radius）
3. 若實作與 Figma 不符，修正後再次比對，並重新確認測試仍為 green
4. **不可用截圖比對**，必須用 Figma MCP 取得節點數值直接對照

---

## 4. 所有任務完成後：完整測試與 Lint

```bash
# 執行專案既有的測試指令（參考 package.json scripts），跑完整測試套件
# 執行 lint
```

若測試或 lint 失敗，修正後繼續，不得跳過。

---

## 5. 輸出實作總結

完整測試套件與 lint 皆通過後，直接輸出總結：

```
## 實作總結

### 修改的檔案
| 檔案 | 對應需求 |
|------|----------|
| path/to/file.tsx | 需求項目 1、2 |
| ... | ... |

### 測試涵蓋
| Spec 場景 | 測試層級 | 測試案例 |
|-----------|----------|----------|
| 正常送出訂單 | E2E | submits an order from the form |
| 訂單編號為空 | 單元測試 | it("shows an error when order number is blank") |
| ... | ... | ... |

### 驗證結果
- 測試：✅ 通過 / ❌ 失敗（說明）
- Lint：✅ 通過 / ❌ 失敗（說明）

### 注意事項（如有）
- 發現但未修改的潛在問題：...
- Spec 中「不在範圍」項目提醒：...
```

輸出後等待使用者手動驗證。

---

## 完成條件
- `/opsx:apply` 執行完成，`tasks.md` 所有任務已打勾
- 每個任務都經過「確認 red → 寫最少實作 → 確認 green」的 TDD 迴圈，且過程中沒有為了遷就實作而修改測試斷言（若有調整，皆已取得使用者同意）
- 所有 UI 修改已透過 Figma MCP 節點比對驗證
- 完整測試套件與 lint 皆通過
- 實作總結已輸出

`implement-issue-with-test` 流程至此結束。
